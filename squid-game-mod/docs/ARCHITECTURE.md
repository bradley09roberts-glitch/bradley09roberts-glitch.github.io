# Architecture guide

Squid Game tournament mod for **Minecraft 1.21.1 / Fabric** (Loader >= 0.16.10, compiled against 0.19.3; Fabric API 0.116.17+1.21.1,
GeckoLib 4.9.3, Java 21, Mojang mappings). This document is the map for anyone adding or changing a game, an arena, an NPC behaviour or a
screen. Read it together with `docs/ARENA_MARKERS.md` (arena contract), `docs/ASSET_CONTRACT.md` (models / animations /
sounds / blocks) and `docs/BUILDING_GUIDE.md` (structure DSL), and use `game/redlight/` as the reference implementation of a
complete game.

## 1. Layers and packages

```
src/main/java/com/squidgame/         COMMON code (runs on dedicated servers, never touches client classes)
  core/        pure Java rules (no Minecraft types): Difficulty, Personality, Appearance, GameKind, Phase,
               redlight/* ...  -> unit tested in src/test/java (JUnit 5, no game launch needed)
  build/       pure Java structure DSL (BlockBuffer, BuildContext, markers/regions) + ArenaBuilder per arena
               (build/arena/<Name>Builder.java, helpers in build/arena/<pkg>/) -> previewable with tools/dump.sh
  world/       dimension plumbing: ArenaWorld, ArenaData (SavedData: built version + markers + regions), BuildJob
               (time-sliced block placement), BuildManager
  tournament/  the state machine: TournamentManager (phases, registration, roster, eliminations, persistence hooks),
               Tournament / Roster / Contestant, Announcer, DoorService, GuardService, Teleporter, Restrictions
               (arena rules), HudService, ChunkLoader, NpcFactory, PlayerStore (snapshots)
  game/        MiniGame + GameContext API and one package per game: redlight/ dalgona/ tug/ marbles/ bridge/ finale/
  entity/      ContestantEntity (NPC / stand-in body), GuardEntity, DollEntity, RopeEntity, MarbleProjectile,
               NpcBehavior + NpcMemory, Activity (synced poses), Anims (animation names)
  net/         payload records + ModNetwork (registration); registry/ block/ item/  vanilla-style registries
  command/     /squid ... commands
src/client/java/com/squidgame/client/  CLIENT-ONLY code (split source set: referencing it from common code does not compile)
  hud/ (SquidHud), screen/ (ScreenRegistry + game screens), render/ (GeckoLib renderers, tracksuit/bib layers,
  rope renderer), net/ClientNetworking, state/ClientState, game/<pkg>/ (per-game screens, overlays, key bindings),
  mixin/WorldOpenFlowsMixin + ExperimentalWorldWarning (see section 11)
src/main/resources/                  assets (geo, animations, textures, sounds, lang), data (dimension, tags)
```

Rules of the road: **the server is authoritative** for every rule, timer, elimination and random outcome. The client only
renders, plays sounds, shows screens and sends *inputs* (`ClientActionPayload`). Never trust a value from the client
without validating it against server state (position, cooldown, phase, whose turn it is).

## 2. The arena complex

* One custom dimension `squidgame:arena` (flat void, fixed noon, no weather; datapack JSON). Seven arenas are placed 1000 blocks
  apart (`ArenaId`: HUB + six game arenas), arena origin at y = 64 (`ArenaId.ORIGIN_Y`).
* Each arena is generated by a pure-Java `ArenaBuilder` into a `BlockBuffer`; `BuildManager` writes it into the world in time slices
  (`buildBlocksPerTick` / `buildMillisPerTick`), fixes neighbour shapes and records **markers** (named points with yaw and
  `k=v` data) and **regions** (named boxes) in `ArenaData`. Games must read positions from markers/regions
  (`ctx.marker("redlight.doll")`), never hard-code coordinates. The marker contract is `docs/ARENA_MARKERS.md`.
* A builder version bump (`ArenaBuilder.version()`) makes the next start rebuild that arena (`/squid build force` forces it).

## 3. Tournament lifecycle (`TournamentManager`, `Phase`)

`REGISTRATION -> INSTRUCTIONS -> COUNTDOWN -> GAME -> ELIMINATIONS -> RESULTS -> TRANSITION -> (next game) ... -> FINAL_WINNER -> RESTART`

* `INSTRUCTIONS`: everyone is moved to the arena's waiting room (marker `waiting.spawn`), the gate door (`gate.door`) is created
  closed, `MiniGame.prepare(ctx)` runs, the title/instructions are announced.
* `COUNTDOWN`: `MiniGame.placeContestants(ctx)` moves every alive contestant to its start position, the gate opens, beeps count down.
* `GAME`: `MiniGame.begin(ctx)` once, then `tick(ctx)` every server tick until `isFinished(ctx)` or the time limit
  (`timeLimitTicks`, scaled by difficulty and `timeScale`); on timeout `onTimeout(ctx)`.
* `ELIMINATIONS`: `MiniGame.conclude(ctx)` eliminates everyone who failed and returns a `GameResult`.
* `RESULTS` shows the results screen (`ResultsPayload`); `TRANSITION` moves survivors back to the dormitory;
  `Planner.next(...)` picks the next game (games whose minimum participant count is not met - `GameKind.minParticipants`: Tug of
  War 4, Glass Bridge 12 - are skipped and announced via `Planner.skipped`; two survivors jump to the final; one survivor wins). `FINAL_WINNER` celebrates; `RESTART` cleans up and optionally starts a new registration.
* Persistence: `TournamentData` (SavedData) stores the tournament + roster + player snapshots; after a server restart the
  tournament resumes (`resumeOnRestart`) at the start of the interrupted game's round or resets cleanly (players restored from
  snapshots). Games persist hidden state through `saveState/loadState` (NBT).
* Disconnects: a human who leaves is replaced by an AI stand-in with the same number (`ContestantEntity`); rejoining takes control
  back (`MiniGame.onControllerChanged`). Humans away longer than `disconnectGraceSeconds` are eliminated. Late joiners spectate.

## 4. Writing a game (`game/<pkg>/<Name>Game implements MiniGame`)

Discovered by name (`GameRegistry.className`): `game/dalgona/DalgonaGame`, `game/tug/TugOfWarGame`, `game/marbles/MarblesGame`,
`game/bridge/GlassBridgeGame`, `game/finale/FinalSquidGame`. Optional companions found by name as well:
`game/<pkg>/<Pkg>Net` (static `register()` for extra payloads) and `client/game/<pkg>/<Pkg>Client` (static `register()` for screens /
renderers); see `ModNetwork.init` and `ScreenRegistry.discoverGameClients` for the exact class names.

`GameContext ctx` is the game's window onto the tournament: `alive()`, `aliveHumans()`, `aliveAi()`, `byNumber()`, `of(player)`,
`npc(contestant)`, `markers()/marker()/regions()/region()`, `eliminate(c, cause[, delay])`, `eliminateByGuard(c, aimTicks)`,
`spawnGuards()`, `doors()`, `assignBehaviors(factory)`, `broadcast/title/actionBar/sound/soundAt`, `danger()` (client vignette),
`fade()`, `screen(player, id, action, data)`, `teleport(...)`, `schedule(ticks, runnable)` (dropped when the game ends),
`difficulty()`, `rng()`, `gameTicks()`.

Conventions:

* **Same rules for players and NPCs.** Humans act through input + server validation, NPCs through a `NpcBehavior` that issues the
  *same* actions (e.g. dalgona: both go through the same needle/crack simulation; marbles: both go through the same bet resolver).
* Per-contestant state lives in `Contestant.gameState` / `Contestant.stats` or a map inside the game; clear it in `prepare`.
* Everything temporary is tagged `squidgame_temp` (entities) and removed in `cleanup` (idempotent; also runs on reset). Restore any
  blocks you changed. Never leave chunk tickets or scheduled tasks behind.
* Difficulty (`ctx.difficulty()`): `timeScale`, `toleranceScale`, `resourceScale`, `npcSkillBonus`, `allowanceScale`;
  derive concrete numbers in a pure `core/<game>/*Rules` class with a table per difficulty and unit-test it.
* Every player-visible string is a translation key in `tools/lang/<game>.json` (merged into `assets/squidgame/lang/en_us.json` by
  `python3 tools/merge_lang.py`).
* HUD: return `HudPayload.Widget`s from `hudWidgets` (bar / counter / banner / light / line); screens use
  `ctx.screen(player, "<id>", OPEN|UPDATE|CLOSE, nbt)` and the client answers with `ClientActionPayload(id, nbt)` that arrives
  in `MiniGame.onClientAction`.
* Edge cases every game must handle: contestant eliminated by the tournament (disconnect, admin) mid-game; everybody failing
  (the tournament continues with 0 survivors => see `Tournament`/`FINAL_WINNER`: no winner), timeout, a human replaced by an AI
  stand-in mid-game, late NPC removal, two eliminations in the same tick.

## 5. NPC contestants

* `ContestantEntity` (GeckoLib) is the body of every NPC and of disconnected humans. Appearance (`core/Appearance`: tint, hairstyle,
  face, glasses...) and `Personality` (courage, reactionSpeed, patience, skill, aggression, cooperation, riskTolerance + archetype)
  are generated from the roster seed and persisted.
* Decisions come from the game's `NpcBehavior` (assigned via `ctx.assignBehaviors`); it steers with the entity's motor helpers
  (`moveToward` = vanilla navigation, `moveDirect`, `stopMoving`, `faceToward`, `lookAtPos`, `leapToward`), sets synced poses
  with `setActivity(Activity.X)` and one-shot gestures with `triggerAction("name")`. The entity handles stuck recovery
  (nudge, re-path, side-step, teleport to the nearest safe floor) and calls `NpcBehavior.onStuck` as a last resort.
* **Information limits**: a behaviour may only use what a human in the same place could know: public game state, what it has seen
  or heard (`NpcMemory.remember/recall`), and its own personality. Hidden server state (the bridge's safe panels, the other
  player's marble count, the dalgona's exact crack threshold) is never read by a behaviour.
* Personality should change *observable decisions*: when to start, how much to risk, who to follow, how long to hesitate, whether
  to cooperate, how likely mistakes are (`Personality.effectiveSkill(difficulty)`, `reactionDelayTicks`, `riskAppetite`).
* Performance: far-away NPCs *decide* at a reduced rate (`npcFarDistance`, `npcFarTickInterval`); keep per-tick behaviour work
  O(1) per NPC (cache path results, throttle searches). Movement itself must stay continuous: vanilla's move control consumes the
  wanted position every tick (`zza` falls back to 0 on the next one), so `ContestantEntity` re-applies the last `moveDirect` target
  on every tick whatever the behaviour's rate (a regression here made far NPCs run at a third of their speed).
* `ContestantEntity.setSpeed` is overridden: vanilla also feeds the speed into `zza`, which makes the pace quadratic in the movement
  attribute. Modifier 1.0 = 4.3 blocks/s (a player's walk), 1.3 ~ sprint.

## 6. Animation

GeckoLib controllers per entity: `locomotion` (idle/walk/run/skid chosen from speed) and `action` (synced `Activity` loops and
one-shots). Animation names are listed in `docs/ASSET_CONTRACT.md` and mirrored in `entity/Anims`. To show a gesture call
`npc.triggerAction("short_name")`; to hold a pose use `npc.setActivity(...)`. Guards: `GuardEntity.setStance(...)`,
`gesture(...)`, `aimAndFire(...)`. The doll: `DollEntity.State` + `setEyes`. Doors and machinery are display entities / blocks
driven by `DoorService` or the game.

## 7. Networking and client UI

All payloads are registered in `ModNetwork` (+ optional game `*Net` classes). Existing payloads: `HudPayload` (phase, timer,
widgets), `OpenScreenPayload` (open/update/close a named screen with an NBT body), `ClientActionPayload` (client -> server input),
`FadePayload`, `DangerPayload` (vignette pulses), `NumbersPayload` (contestant numbers for tracksuit rendering),
`ResultsPayload`. Client screens register in `ScreenRegistry` by id.

## 8. Rules enforcement (`Restrictions`)

While a player is a contestant in the arena dimension: build/break/place/use items, fly, enderpearl/chorus/teleport commands,
equipment changes, container access (any block with a menu provider), damage and leaving the bounds are blocked or reverted
(`Restrictions.tickPlayer` runs every tick for every player in the arena dimension: gamemode, abilities, forbidden items every 10
ticks, and any jump of more than 12 blocks that the mod did not announce with `noteTeleport` is undone with a position packet;
`TournamentManager.enforceBounds` handles humans outside `arena.bounds` during a game). `/squid debug rules <player>` prints why a
player is or is not restricted. Note for tests: a vanilla `/tp` run from RCON uses the *overworld* as its level, so use
`/execute in squidgame:arena run tp ...` to test inside the complex; the player's gamemode, inventory,
position, health and effects are snapshotted on entry and restored on exit (`PlayerStore`). Operators bypass when
`allowOpsToBypassRules`. Game-specific exceptions (e.g. holding the marble item) go through the game, not through Restrictions.

## 9. Config (`config/squidgame.json`, `/squid config <key> [value]`)

## 10. Development and testing

* Unit tests: `./gradlew test` (JUnit 5; `core/` has no Minecraft dependency).
* Arena iteration without launching Minecraft: `tools/dump.sh <arena>` then `tools/preview.py` / `tools/check_markers.py`.
* Dedicated server for tests: `tools/devserver.sh start|stop|restart|log` (deploys `build/libs/squidgame-*.jar`; set
  `SQUID_ACCEPT_EULA=1` to accept the Minecraft EULA yourself), RCON via `tools/rcon.py "<command>"` (password `squidtest`).
* Debug commands (op): `/squid debug play <game> [npcs] [difficulty]` runs a single game with you as a contestant (registration is
  skipped, the tournament ends after the game), `/squid debug simulate [npcs] [difficulty]` runs a whole NPC-only tournament,
  `/squid debug timescale <x>` shortens all timers, `/squid debug eliminate <number>`, `/squid debug roster`,
  `/squid debug markers <arena>`, `/squid skip` skips the current phase.
* Headless client with screenshots: `tools/xvfb-client.sh [display]` (Xvfb + llvmpipe; env `SQUID_USER`, `SQUID_RUNDIR` allow several
  clients, e.g. a second one on display 99) and `DISPLAY=:98 import -window root shot.png`; `tools/xinput.py` scripts mouse and keys
  (clicks move the pointer, which turns the camera while the cursor is captured: use `down 3` / `up 3` to click in place and
  `tp @s ~ ~ ~ facing entity <name> eyes` with `execute anchored eyes` to aim).
* Single-player: `tools/spclient.sh` creates a fresh world with a throwaway server (needs `SQUID_ACCEPT_EULA=1`) and opens it in the
  integrated server of a headless client.
* Reconnect without restarting a client: set `accepts-transfers=true` in `server.properties` and run `transfer localhost <port> <name>`.
* Smoke test: `tools/smoke.sh [npcs] [difficulty]` runs a complete NPC-only tournament at 100 ticks/s and fails on server errors.
* `/squid debug playopen <game> [npcs] [difficulty]` is `play` with the registration left open for more players (two humans in one game).
* Packaging: `tools/package.sh` builds and assembles `dist/` (mod jar, Fabric API, GeckoLib, SHA256SUMS, INSTALL.txt).

## 11. The experimental-settings prompt (client mixin)

Minecraft flags every world with more than the three vanilla dimensions as experimental (`WorldDimensions#bake`) and asks for a
confirmation each time it is opened (`WorldOpenFlows#openWorldCheckWorldStemCompatibility` -> "Worlds using Experimental Settings are
not supported"). The complex lives in the fourth dimension `squidgame:arena`, so `client/mixin/WorldOpenFlowsMixin` skips that prompt
when `ExperimentalWorldWarning.onlyBecauseOfArenaDimension` says the arena dimension is the only reason (no experimental feature
flags enabled, not an old customised world). The mixin is registered for the client only (`squidgame.client.mixins.json`,
`required: false`, `defaultRequire: 0`): if it ever fails to apply the vanilla prompt simply returns. With Loom 1.17 the production
remapping of the mixin annotations is done by tiny-remapper at `remapJar` time (no refmap, no annotation processor): the built jar's
`WorldOpenFlowsMixin.class` carries the intermediary names (`class_7196`, `method_57775` ...).
